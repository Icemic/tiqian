# Android OEM 字体行为脱敏汇总

这份汇总来自 11 份经校验的自愿提交证据包，覆盖 API 26–36，其中 8 份具备逐 glyph 字体读回。
原始 ZIP、机器目录、标签文件和 archive hash 只保留在本地研究工作区，不进入 Git。公开文档不保留
build fingerprint、incremental 版本、精确机型、采集时间、完整字体路径、字体文件哈希或可回连原包
的标识。

## 直接观测

- 8/8 份逐 glyph 样本中，默认中文正文与中文标点使用同一字体实例集合。
- 8/8 份逐 glyph 样本中，默认 emoji 使用独立的系统彩色 emoji 字体。
- 8/8 份逐 glyph 样本的默认西文都不符合旧实现“从无序字体集合优先猜 Roboto”的规则。
- 可变字体的实际默认实例出现过 `wght=310`、`399`、`640`，另有 API 35+ 的 weight override
  `310` 与 `412`；把平台结果统一改写成 `400` 会改变轮廓、advance 和断行输入。
- 三份 API 31+ 小米样本中，中文标点都随 MiSans 中文正文实例，没有观测到 Noto 接管中文标点。
- 一组同设备受控对照分别使用系统默认字体与字体模块：352 条共同请求中有 292 条的 glyph 读回、
  栅格或 run metrics 发生变化，证明运行时字体设置不能从静态系统字体枚举推断。
- 一份 API 36 样本的默认正文实际来自数据分区字体，证明只扫描 system/product 字体目录不足以表达
  主题字体或运行时替换。

## 按平台分组的现象

- 华为 API 31：中文与西文由不同的 HarmonyOS Sans 实例承担；两份样本的中文有效字重不同。
- OnePlus API 36：系统默认时中文与西文分开，启用字体模块后同一运行时字体接管两者。
- 小米 API 34/36：MiSans 的中文、西文和标点关系随系统版本与字体配置变化，且实际实例可能依赖
  可变轴或 style override。
- vivo API 36：观测到运行时数据分区字体同时承担中文与西文。
- API 26/29：只能保留宽度、栅格和配置声明；没有逐 glyph 字体读回，不能据此补造实际 face。

## 使用边界

- 这些统计用于否定旧实现的错误假设，不把任一 OEM 行为提升为通用规范。
- `PositionedGlyphs` 不提供 glyph 到 UTF-16 cluster 的映射；同一 probe 混用字体时，不能凭 glyph
  顺序给源码字符补造映射。
- 字体配置 XML 是声明证据；主题引擎、字体模块和运行时替换必须由同一次 platform shaping 读回确认。
- 不同设备之间存在系统版本、主题和用户设置等混杂因素；只有采集条件明确的同设备对照适合因果归因。
